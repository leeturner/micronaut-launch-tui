# Slice 8: Distribution

Part of the [roadmap](../../roadmap.md). This is slice 8 of 8. It builds on
[slice 7](2026-10-11-help-and-readme-design.md).

## Why

Today `mtui` runs as `java -jar` on a shadow jar behind a shell alias, which
needs Java 25 and a local build. The user wants to download a single `mtui`
binary from GitHub Releases instead.

For now the user is the main user. Anything fancier (Homebrew, SDKMAN) waits
until someone else shows interest. This slice copies the setup of Dan Vega's
[spring-initializr-tui release workflow](https://github.com/danvega/spring-initializr-tui/blob/master/.github/workflows/release.yml),
using Gradle instead of Maven.

## What a spike proved

A throwaway spike (branch `spike/native-image`) built `mtui` as a GraalVM CE 25
native image on macOS arm64. The user ran the whole flow with it: name screen,
versions and options loaded from Launch, search, toggling, preview, `?` help,
generating, unzipping and `--open`. The binary is about 72 MB and needs no other
files. It took three changes, which this slice keeps:

1. A `graalvmNative` block in `build.gradle.kts` sets `imageName = "mtui"`.
   Without it the binary is named after the project, `micronaut-launch-tui`.
2. The same block adds the build arg `--enable-native-access=ALL-UNNAMED`.
   It's the native version of the `Enable-Native-Access` attribute the shadow
   jar already sets in its manifest. Without it, JLine prints a "restricted
   method" warning.
3. `src/main/resources/META-INF/native-image/com.leeturner/mtui/reachability-metadata.json`
   registers two things native image can't find on its own:
   - for reflection, logback's `ch.qos.logback.core.status.NopStatusListener`
     with its no-arg constructor; logback creates it from `logback.xml`
   - as resources, the glob `dev/tamboui/tui/bindings/*.properties`; without
     them TamboUI crashes on start with "Built-in bindings not found"

Missing metadata fails **at runtime, not at build time**. A green build doesn't
prove the binary works.

## What it does

### Releasing

- Pushing a tag `v<version>` (e.g. `v0.2.0`) runs a new workflow,
  `.github/workflows/release.yml`.
- The workflow builds the native image on three GitHub-hosted runners using
  GraalVM 25:

  | Platform | Runner | Archive |
  |---|---|---|
  | macOS arm64 | `macos-latest` | `mtui-<version>-macos-aarch64.tar.gz` |
  | Linux x86_64 | `ubuntu-latest` | `mtui-<version>-linux-x86_64.tar.gz` |
  | Windows x86_64 | `windows-latest` | `mtui-<version>-windows-x86_64.zip` |

  Each archive holds just the binary, `mtui` (or `mtui.exe`), at its top
  level. The tarballs keep the executable bit.
- After building, each runner runs `mtui --version` and checks that it prints
  the version. It's a cheap check that the binary starts. It won't catch a
  crash when the TUI starts, like the TamboUI one above.
- A final job creates the GitHub Release for the tag with the three archives
  attached and release notes generated by GitHub.
- `<version>` is the tag without its leading `v`.
- The workflow can also be started by hand (`workflow_dispatch`). That runs
  the three builds and the `--version` checks but skips the release job, so
  Linux and Windows problems can be fixed without publishing anything.
- The user pushes the release tag, after this slice is merged to `main`.

### Version

- `mtui --version` prints the version, e.g. `0.2.0`. Today it prints nothing.
- The release workflow passes the version from the tag into the Gradle build.
  Builds without a tag get the version `dev`. That replaces the hard-coded
  `0.1` in `build.gradle.kts`, so the shadow jar becomes
  `micronaut-launch-tui-dev-all.jar`. The README's `java -jar` and alias
  lines, and the vhs tapes if they name the jar, change to match.

### Logging

- `logback.xml` logs at `error` instead of `info`. The log at
  `~/.mtui/mtui.log` was filling with response payloads. (Already changed on
  this branch, uncommitted.)

### README

- A new "Install" section, before "Build and run", covers:
  - downloading the archive for your platform from the latest release
  - unpacking it and putting `mtui` on your `PATH`
  - the macOS Gatekeeper workaround for an unsigned binary
    (`xattr -d com.apple.quarantine mtui`)
- "There are no prebuilt downloads yet" goes.
- "Development" says how to build the native image locally: GraalVM 25, then
  `./gradlew nativeCompile`, with the binary at
  `build/native/nativeCompile/mtui`.
- The Windows binary is marked as built but untested.

### Roadmap

- Slice 8 is marked done.
- "Possible later" gains a Homebrew tap, SDKMAN, macOS signing and
  notarisation, and more platforms (Linux arm64, macOS Intel), and a Linux binary for older
  glibc or a static musl build.

## Constraints

- GraalVM native image can't cross-compile, so each platform needs its own
  runner.
- Gradle must run on Java 25. On Java 26, kapt fails (see `.sdkmanrc`). The
  GraalVM set up in CI must be a Java 25 build.
- The user has no Windows machine. Windows counts as done once it builds,
  passes the `--version` check and is attached to the release. Linux is in the
  same position unless the builder can try it in a container. macOS is
  checked by the user.

## Calls made in this spec

These are Claude's calls. The user can change them:

- Archives (tar.gz and zip) holding a binary called `mtui`, rather than bare
  binaries with the platform in the file name.
- The release runs on a `v*` tag push. A manual run builds without
  releasing. Neither runs the tests again; `build.yml` already runs them on
  `main`.
- The user, not Claude, pushes the release tag.
- Untagged builds are version `dev` instead of `0.1`.
- Linux is built on `ubuntu-latest`, so the binary needs a recent glibc
  (Ubuntu 24.04 era). Older distros and a static musl build are for later.
- GraalVM Community Edition in CI, to match the spike, rather than Oracle
  GraalVM, which Dan's workflow uses.
- `mtui --version` as the only automated check of the binary.

## Left to the builder

- How the version gets from the tag into Gradle and into picocli's
  `--version`, e.g. a Gradle property plus a picocli version provider, or a
  generated resource.
- The exact actions and their versions (`graalvm/setup-graalvm`, the MSVC setup
  on Windows if `setup-graalvm` doesn't already provide it, artifact upload
  and download, creating the release), pinned the way `build.yml` pins its
  actions.
- Fixing any native-image problems that only show up on Linux or Windows
  builds.

## Not in this slice

- Homebrew tap, SDKMAN, Scoop, JReleaser.
- Code signing and notarisation.
- Building the native image on every pull request, or a test that starts the
  TUI from the native binary.
- Windows quirks in `--open` (`code` on Windows is `code.cmd`, which
  `ProcessBuilder` won't start without `cmd /c`). Slice 6 deferred this here.
  With no way to test on Windows, it stays deferred.

## Done when

- Pushing `v0.2.0` produces a GitHub Release with the three archives.
- The macOS archive, unpacked, gives `mtui` that the user runs through the
  whole flow, and `mtui --version` prints `0.2.0`.
- The Linux and Windows jobs build, pass the `--version` check and attach
  their archives.
- `~/.mtui/mtui.log` only gets errors.
- The README has the Install section, and the roadmap marks slice 8 done.
